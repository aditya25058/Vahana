# Vahana v0.2 design: any PC, any OS, the same answers

Status: proposal, 2026-11-20.

## Goal
Anyone can install Vahana and run a MoE model on the machine they have: Windows, Linux or macOS; x86 or ARM; NVIDIA, AMD, Apple or no GPU at all.

**The promise that makes this worth doing:** the same model and the same prompt give **the same tokens on every machine**, bit for bit, from a laptop CPU to an H100. Every other engine's output changes with the hardware.

**What does not change with software:** the model must fit in RAM plus fast disk. "Any PC" means Vahana tells you which models your machine can run, and runs them exactly. It does not mean 236B on 16 GB.

## Where v0.1 is tied to one machine
| Dependency | v0.1 | Fails on |
|---|---|---|
| CPU kernel ISA | AVX-512 + VBMI only (`-march=znver4`) | every Intel consumer CPU before 2024, AMD before Zen 4, all ARM (Apple, Snapdragon) |
| Threading | OpenMP (libgomp) | macOS (no OpenMP by default), MSVC (OpenMP 2.0 only) |
| OS calls | `move_pages`, `numaif.h`, `set_mempolicy`, `libcudart.so`, libc `mmap` via ctypes | Windows, macOS |
| Build | `bash build_kernel.sh` with g++ | Windows, users without a compiler |
| GPU | NVIDIA + Triton required for attention and linears | no GPU, Apple GPUs, Windows without Triton |
| Memory | experts resident in RAM | machines with less RAM than the model |
| Cross-device exactness | CPU == GPU for experts and linears only; attention uses the GPU's `exp` | a CPU-only machine could not match a GPU machine's tokens |

## Design
### 1. One CPU kernel, every ISA, identical bits
- **Same lanes everywhere.** The twin arithmetic is defined as 16 fp32 FMA lanes, k ascending, then a fixed tree. Every path computes exactly this:
  - AVX-512: 1 register;
  - AVX2 + FMA3: 2 × 8 lanes (Haswell / Zen 1 and newer);
  - ARM NEON: 4 × 4 lanes, `vfmaq_f32`;
  - scalar: 16 `fmaf` accumulators.

  Fused multiply-add is exact IEEE-754 on all of them, so the bits match by construction.
- **NX12 decode per ISA:** AVX-512 VBMI (today), AVX2 `pshufb`, NEON `tbl`. Raw BF16 always works.
- **Runtime dispatch** picks the best path the CPU has. `VAHANA_ISA=avx2|scalar|…` forces one, for testing.
- **Our own thread pool** (std::thread + atomics) replaces OpenMP, so the kernel builds the same way with GCC, Clang and MSVC. NUMA placement stays as an optional Linux-only extra.
- **Compiler rules:** no FP contraction on any compiler (`-ffp-contract=off`, `/fp:precise /fp:contract-`). `exp` is Vahana's own polynomial everywhere.

### 2. CPU-only Vahana, and GPU attention that matches it
- **Every layer runs on the CPU when there is no usable GPU:** experts, twin linears, norms, and a CPU twin of the `vahana` attention function.
- **The GPU attention kernel switches to Vahana's `exp` and the CPU twin's block order,** so GPU and CPU attention give the same bits. Then **a CPU-only laptop and an H100 produce identical tokens**, and any placement is valid.
- Triton covers NVIDIA, AMD ROCm and Intel XPU. Apple GPUs run CPU-only at first; Apple Silicon has fast unified memory and NEON. Metal kernels come later.

### 3. Portable build and OS layer
- **Prebuilt wheels** (cibuildwheel) for Linux x86-64 / arm64, Windows x86-64 and macOS arm64, all ISA paths in one binary. No compiler is needed to install.
- **The Python OS layer** uses the standard `mmap` module, finds the CUDA runtime per platform (`cudart64_12.dll` / `libcudart.so.12`), and makes the NUMA policy and page placement optional, Linux-only.
- **The CUDA host-node graph** is kept on every OS that has CUDA. Elsewhere decode runs eagerly.

### 4. Fit the machine
- **`vahana doctor`** reads CPU, ISA, RAM, GPU and disk, and lists which models run exactly on this machine and at what estimated speed.
- **Streaming tier:** when the experts exceed RAM, keep an expert cache in RAM and stream the rest from the OS page cache / NVMe. The answers stay bit-identical; only speed changes.
- **Reproducible quantized tier** (opt-in, clearly labelled): int8 / int4 experts with a fixed dequantise order. Not equal to BF16, but the same bits on every machine: reproducible, not "exact to BF16".

## Milestones (each pre-registered like M0-M5)
| # | Deliverable | Done when |
|---|---|---|
| P1 | Portable kernel: thread pool, AVX-512 / AVX2 / NEON / scalar dispatch | All 19 M2 cases bit-identical across every x86 path forced on the H100; AVX-512 speed within 3% of v0.1; the AVX2 path builds and matches on this Windows laptop (WSL and native) |
| P2 | CPU-only Vahana + twin attention (GPU uses Vahana's `exp`) | Tiny families: CPU-only logits == GPU logits, bit for bit; batch invariance still holds |
| P3 | Windows and macOS builds, OS layer, wheels, CI matrix | `pip install vahana` works on Linux / Windows / macOS; the same tiny-model logits hash on all three in CI |
| P4 | `vahana doctor` + streaming tier | On this laptop (15 GB RAM, 4 GB GPU): OLMoE-1B-7B runs exactly; Qwen3-30B runs exactly from NVMe, with speed reported |
| P5 | Reproducible quantized tier | int8 / int4 experts identical across ISAs and devices; quality reported vs BF16 |
| P6 | AMD / Intel GPUs via Triton | Tiny families exact on ROCm (when hardware is available) |

## Risks
- **AVX2 NX12 decode** may not beat raw BF16. Then AVX2 machines use raw BF16, which is still exact.
- **MSVC floating-point behaviour** must be verified bit for bit (contraction, denormals). The cross-ISA hash test catches any drift.
- **Triton on Windows** is community-maintained. If it fails, Windows uses CPU attention, which is still exact.
- **Consumer machines are slow for large MoEs.** `vahana doctor` must say so honestly before a download, not after.
