# Vahana v0.1 design: one adapter for every MoE model

Status: proposal, 2026-11-20.

## 1. Goal and scope
**v0.1 promise:** any Mixture-of-Experts causal LM that `transformers` can load runs on Vahana:
- **Weights:** BF16 checkpoint.
- **Hardware:** one GPU plus a big-RAM CPU host.
- **Placement:** all routed experts in CPU RAM.
- **Exactness:** the output tokens are bit-identical to Vahana's own all-GPU reference, whatever the GPU budget, expert placement, batch size or thread count.

Not in v0.1: FP8 / MXFP4 checkpoints, multi-GPU, encoder-decoder MoE, desktops with too little RAM for the experts. Each is noted where it fits.

**What "exact" means.** Each token's result is a fixed function of the weights and that token's own history. Vahana defines the arithmetic, and every device computes it bit for bit:
- **Twin arithmetic:** 16 fp32 FMA lanes over k ascending, a fixed tree reduction, BF16 round-to-nearest-even at fixed points.
- **Batch-invariant kernels:** each row's reduction order depends only on fixed tile sizes, never on batch size or padding.

The reference run puts every expert on the GPU through the same twin kernels. Stock `transformers` uses cuBLAS, which is neither batch-invariant nor device-invariant, so it is not the reference. Quality against stock fp32 is still measured and reported.

## 2. What the survey found (transformers 5.12, 32 MoE families)
`transformers` 5.x gives MoE one structure. A decoder layer's MLP is a sparse block that:
1. calls a **router** module that returns `(logits, top_k_weights, top_k_index)`, or computes routing inline;
2. calls **`experts(hidden, top_k_index, top_k_weights)`**. All experts live in one module as 3-D tensors (`gate_up_proj [E, 2I, H]`, `down_proj [E, H, I]`), and the module returns the weighted sum;
3. optionally adds **shared experts**, a plain gated MLP. Some families scale the shared output by a sigmoid gate (Qwen2-MoE, Qwen3.5-MoE).

| Variation | Families |
|---|---|
| **Standard experts:** fused `gate_up_proj` (gate = first I rows, up = next I rows), `down_proj`, SiLU-GLU, no bias | Mixtral, Qwen2/3/3.5-MoE, OLMoE, DeepSeek-V2/V3/V3.2, GLM-4-MoE (+Lite, DSA), Ernie-4.5-MoE, Phi-MoE, Jamba, MiniMax (+M2), Hunyuan-MoE, LFM2-MoE, AFMoE, Cohere2-MoE, Exaone-MoE, Qwen3-VL/Omni-MoE text |
| Interleaved gate/up, expert biases, clamped SwiGLU (`alpha`, `limit`, `up + 1`) | gpt-oss |
| Clamped activation (`limit`) | DeepSeek-V4 |
| Transposed layout `[E, H, 2I]`; every expert evaluated on router-scaled inputs | Llama 4 |
| `ParallelExperts` (`input_linear` / `output_linear`) | Granite-MoE (+shared, hybrid), JetMoE |
| Custom expert containers | DBRX, NLLB-MoE |
| **Router:** softmax → top-k (± renormalise) | Mixtral, Qwen, OLMoE, MiniMax, Jamba, Hunyuan, Granite, JetMoE, Cohere2, gpt-oss (top-k → softmax, with bias) |
| **Router:** softmax, group-limited top-k, scaled | DeepSeek-V2 |
| **Router:** sigmoid + correction bias, group top-k, renormalise, scale | DeepSeek-V3/V3.2, GLM-4-MoE, Exaone-MoE, MiniMax-M2, AFMoE, LFM2-MoE |
| **Router:** unusual | Phi-MoE (sparsemixer), Llama 4 (top-k, then sigmoid on inputs), DeepSeek-V4 (hash router on some layers), Ernie (correction statistics) |
| **Attention:** non-standard | MLA (DeepSeek, GLM-Lite); sparse indexer (DeepSeek-V3.2, GLM-DSA); sinks + sliding window (gpt-oss); Mamba / Gated-DeltaNet / short-conv layers (Jamba, Granite-hybrid, Qwen3.5, LFM2); mixture-of-attention (JetMoE) |

**Conclusion:**
- Routers vary a lot, but they are small GPU-side code that Vahana does not need to rewrite.
- Experts vary little: one layout covers ~25 families, and five more need a small adapter each.
- The natural seam is the **`experts(hidden, top_k_index, top_k_weights)` call**.

## 3. Architecture
```
HF model (meta device, built from config)
 ├─ attention, norms, embeddings, router, shared experts  -> run HF's own code, made invariant (§3.4), on the GPU
 │                                                            (or as CPU twin linears when the GPU budget is short)
 └─ every MoE block's `experts` module                     -> replaced by VahanaExperts (§3.3)
                                                               weights in CPU RAM (NX12, socket-placed),
                                                               computed by the CPU twin kernel
```

### 3.1 ModelSpec: discover the structure, never hard-code families
`vahana.spec.inspect(model, config) -> ModelSpec` walks the meta-device model once. For each decoder layer it records:
- **the MoE block:** a module with an `experts` child, found by structure, not by class name;
- **the experts layout,** detected from parameter names and shapes, with a per-class override table for the few layouts that cannot be detected:
  - `fused_concat` (`gate_up_proj [E, 2I, H]`, `down_proj [E, H, I]`);
  - `fused_interleaved` (gpt-oss);
  - `fused_transposed` (Llama 4);
  - `parallel_experts` (Granite / JetMoE);
  - `module_list` (remote-code models such as the original DeepSeek-V2);
- **the activation:** from `config.hidden_act` and the experts class (`silu_glu`, `gelu_glu`, `swiglu_clamp(alpha, limit, up_plus_one)`, `silu_glu_clamp(limit)`);
- **biases** on gate_up / down;
- **E, I, H, top-k,** and whether shared experts and a shared-expert gate exist;
- **dense layers** (`first_k_dense_replace`, `mlp_only_layers`, `decoder_sparse_step`), which stay ordinary MLPs.

A family whose experts module is not recognised fails loudly with its class name. It never falls back silently.

### 3.2 ExpertStore: weights from the checkpoint, never through the model
- Expert parameters never materialise on the meta model. The store reads them straight from the safetensors shards.
- **Key mapping** reuses `transformers.conversion_mapping` (`get_checkpoint_conversion_mapping`, `WeightConverter`: MergeModulelist / Concatenate / Chunk / Transpose). The checkpoint layout (per-expert `experts.{e}.gate_proj`, Mixtral `w1/w3/w2`, or already-fused) therefore maps to the model's fused parameters by HF's own rules.
- **Per expert,** the store produces row-major `gate [I, H]`, `up [I, H]`, `down [H, I]` (+ biases). From those it:
  - NX12-encodes the matrices (lossless; 75% of BF16);
  - places each matrix's row halves on the two sockets;
  - applies the RAM guard (raw BF16 when MemAvailable would fall below the margin).
- **A cache file** of the encoded store is optional, so later starts skip encoding. Startup is disk-bound, so this saves ~20%.

### 3.3 VahanaExperts: the one replacement module
`VahanaExperts.forward(hidden, top_k_index, top_k_weights)` has the same signature and return as the HF experts module:
- **Decode** (few rows): one CPU job per layer through the persistent worker. This is the fused v16 kernel: all selected experts in one region, per-expert counters, padded work counters.
- **Prefill** (many rows): the same kernel's batched path.
- **Combine:** per token, experts in ascending id, `acc = y0·w0; acc = acc + yj·wj` in fp32, then BF16. That fixes the order, unlike HF's `index_add_` in BF16.
- **Shared experts** remain HF modules (GPU or CPU twin linears). The fused-shared CPU path stays as an optional fast path when the shared expert is a plain ungated GLU.

**Kernel generalisation (csrc/cpu_moe.cpp):**
- an activation enum and parameters per registered layer;
- optional gate/up/down biases;
- raw-BF16 fallback when I or H is not a multiple of 64 (NX12 decode works in 64-wide steps);
- I and H as runtime values (already true).

The twin arithmetic does not change.

### 3.4 Invariance layer
- **Linears:** `nn.Linear` goes to the batch-invariant GEMM (GPU) or the twin linear (CPU), class-wide, as today. The fp32 router fast layout (Phase 41) is applied to any router whose weight is used in fp32.
- **Norms:** RMSNorm / LayerNorm modules go to invariant kernels, matched structurally as today.
- **Attention:** register a `vahana` entry in `transformers`' `ALL_ATTENTION_FUNCTIONS` and set `config._attn_implementation = "vahana"`. One fixed-order kernel covers MHA / GQA / MQA, causal, sliding window, sinks and logit soft-capping, so every standard-attention family is invariant with no per-family code. MLA keeps Vahana's latent kernel and is used when the attention module is MLA.
- **Routers:** HF's code runs unchanged. softmax / sigmoid / top-k are row-local and deterministic, and their matmuls go through the invariant linear.
- **Recurrent / conv layers** (Mamba, Gated-DeltaNet, short conv) run HF's kernels. These are exact at batch 1 (same inputs, same kernels); batch invariance for them is a v0.2 item.

### 3.5 Generic decode graph
Today Vahana has two hand-written graph decoders, one per family (`graph_decode.py` for DeepSeek, `mixtral_graph.py` for Mixtral). v0.1 replaces both with one mechanism:
- Capture **one CUDA graph per decode step** over the unmodified HF forward, with a static KV cache.
- Inside `VahanaExperts` during capture, record:
  - device→pinned copies of hidden / indices / weights;
  - a **host node** (`cudaLaunchHostFunc`, from the C++ extension) that runs the CPU expert job and returns when it completes;
  - a pinned→device copy of the result.
- Stream order then serialises GPU work, CPU experts and GPU work with no Python on the critical path.

**Risk:** host callbacks run on a CUDA driver thread. The callback must only signal the persistent OpenMP worker and wait. It must not call CUDA, and must not be the OpenMP master. Milestone M0 tests this before anything depends on it. The fallback is today's per-layer segmented capture, generated from ModelSpec instead of written per family.

### 3.6 Placement and budget
- **On the GPU:** attention, routers, shared experts, embeddings, norms and lm_head, within `--gpu-budget`.
- **On the CPU:** any overflow, as twin linears (Phase 30 machinery).
- **Routed experts:** always on the CPU in v0.1. GPU-cached hot experts are a v0.2 option that leaves the bits unchanged.

### 3.7 Run-time defaults (the Phase 41 lessons, no flags needed)
- NUMA balancing off for the process.
- Main thread moved off the worker's core.
- Fused kernel.
- NX12 for decode.
- Socket placement.
- OMP threads = physical cores minus 2.
- Everything stays overridable through one config object; the `VAHANA_*` environment variables remain for experiments.

## 4. Exactness and test matrix
**Per family, CI-sized** (a tiny model built from the real config with small dims and random weights, a few MB each; no downloads):
1. `VahanaExperts` (CPU) == GPU twin reference, bitwise, for prefill and decode.
2. Batch invariance: each row's logits are identical alone and inside a batch of 4 with different lengths.
3. Thread invariance: 8 vs 24 OMP threads give identical bits.
4. Placement invariance: tokens are identical across GPU budgets.

**Real weights** (H100 box), 128 greedy tokens:

| Model | Family checks | Exact bar | Speed check |
|---|---|---|---|
| OLMoE-1B-7B | softmax router, no shared | ids == reference | report |
| Qwen1.5-MoE-A2.7B | shared expert + sigmoid gate | ids == reference | report |
| Qwen3-30B-A3B | 128 experts, top-8, I = 768 | ids == reference | report |
| DeepSeek-V2-Lite | MLA, group routing, shared | ids == reference | report |
| Mixtral-8x7B | regression | ids == Phase 42 | ≥ 11 tok/s (48 thr) |
| DeepSeek-Coder-V2 236B | regression | ids == Phase 41 | ≥ 7.0 tok/s (48 thr, 16 GB) |

**Quality:** the maximum logit difference from stock `transformers` fp32 on 50 prompts, reported per model.

## 5. Support tiers for v0.1
- **Tier 1, in v0.1** (standard experts and standard or MLA attention):
  - Mixtral, Qwen2-MoE, Qwen3-MoE, OLMoE, DeepSeek-V2, DeepSeek-V3, GLM-4-MoE (+Lite);
  - MiniMax, MiniMax-M2, Hunyuan-MoE, Ernie-4.5-MoE, Cohere2-MoE, Exaone-MoE, AFMoE, Phi-MoE, Granite-MoE (+shared).
- **Tier 2, v0.1 if time allows, else v0.2:**
  - gpt-oss (biases, clamped SwiGLU, and MXFP4 weights, which need dequantise-on-load or a kernel path);
  - Llama 4 (all-experts formulation);
  - DeepSeek-V3.2 / GLM-DSA (sparse indexer attention);
  - DeepSeek-V4 (hash router, clamp);
  - hybrids: Jamba, Qwen3.5-MoE, LFM2-MoE, Granite-hybrid;
  - multimodal text towers: Qwen3-VL-MoE, Qwen3-Omni.
- **Out of scope:** DBRX (custom container; revisit on demand), JetMoE (mixture-of-attention), NLLB-MoE (encoder-decoder).

Any FP8 checkpoint (DeepSeek-V3/R1 and many Qwen3 releases) needs an FP8 path. Converting to BF16 at load is exact for the values, but doubles RAM. A native FP8 twin kernel is the v0.2 item that makes 671B models fit.

## 7. Risks
- **Host nodes in captured graphs (M0)** could add latency or conflict with the OpenMP worker. The fallback is known (segmented capture).
- **transformers internals move.** The adapter depends on the `experts(hidden, idx, w)` call and on `conversion_mapping`. Pin a minimum version and keep a per-class override table.
- **RAM.** BF16 experts need 0.75 × the expert bytes as NX12. Most models over ~600B parameters do not fit in 512 GB without FP8 support.
- **Speed regressions while generalising.** The Mixtral and 236B bars in §4 guard the existing results.
